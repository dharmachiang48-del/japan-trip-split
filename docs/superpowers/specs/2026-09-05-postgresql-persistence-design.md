# PostgreSQL 多人分帳持久化設計

## 背景與目標

目前 WebSocket 後端將每個房間的完整狀態寫入 `server/data/*.json`。Render 服務沒有掛載持久化儲存，因此執行個體休眠、重啟或重新部署後，檔案會回到 GitHub 映像內提交的舊版本，造成成員與支出紀錄恢復成初始狀態。

本次修改的目標是以 Neon PostgreSQL 作為正式環境的中央資料來源，讓不同裝置與多人共同使用同一房間，且 Render 重啟或部署後仍能讀回最新資料。WebSocket 繼續負責即時通知，瀏覽器 `localStorage` 只作為畫面啟動與短暫離線時的快取。

## 範圍

### 包含

- 新增 PostgreSQL 房間儲存層。
- 以 `DATABASE_URL` 連線 Neon，連線字串只存在 Render 環境變數。
- 在正式環境啟動時建立必要資料表。
- 房間加入、完整同步、成員更新及支出新增／修改／刪除都經過同一個持久化介面。
- 保留 JSON 檔案儲存實作，供未設定 `DATABASE_URL` 的本機開發使用。
- 保留每個房間各自的瀏覽器快取，但資料庫已有資料時以伺服器為準。
- 加入自動化測試，證明後端重新建立後仍可由持久化儲存讀回房間。
- 更新部署說明，列出 Neon 建立資料庫與 Render 設定 `DATABASE_URL` 的步驟。

### 不包含

- 會員登入、權限角色或房間密碼。
- 照片及 OCR 圖片的雲端保存。
- 歷史版本、稽核紀錄或逐筆事件溯源。
- 多個後端執行個體之間的跨程序 WebSocket 廣播。

## 方案比較與決策

1. Render Persistent Disk：改動少，但資料與單一 Render 執行個體綁定，不適合作為長期的共享資料層。
2. 瀏覽器 `localStorage` 回填：不需資料庫，但只有持有最新快取的裝置能恢復，清除瀏覽器資料或舊裝置先連線都可能造成資料不完整。
3. PostgreSQL：需要外部資料庫與連線設定，但能讓所有裝置共用中央資料，並獨立於 Render 執行個體生命週期。

採用方案 3，供應商選用 Neon。程式使用標準 PostgreSQL `DATABASE_URL`，避免綁死特定供應商。

## 架構

後端新增獨立房間儲存介面，WebSocket 處理程式不直接操作檔案或 SQL：

```text
瀏覽器操作
    │
    ▼
WebSocket 房間狀態
    │ 先持久化成功
    ▼
RoomStore 介面 ─────► PostgreSQL（正式環境）
    │
    └───────────────► JSON 檔案（本機備援）
    │
    ▼
廣播最新狀態給同房間其他瀏覽器
```

儲存介面提供以下能力：

- `init()`：初始化連線與資料表。
- `load(roomId)`：讀取房間完整狀態；不存在時回傳 `null`。
- `save(roomId, state)`：完整覆寫該房間狀態並更新版本時間。
- `close()`：測試或正常關閉時釋放資源。

伺服器在接受連線前先完成 `init()`。若初始化失敗，程序啟動失敗並輸出明確錯誤，避免網站看似可用但實際只寫入暫存記憶體。

## 資料模型

資料表 `rooms`：

| 欄位 | 型別 | 規則 | 用途 |
|---|---|---|---|
| `room_id` | `TEXT` | Primary key | 房間識別碼 |
| `state` | `JSONB` | Not null | 標題、成員、支出及應用程式版本資訊 |
| `version` | `BIGINT` | Not null | 單調增加的狀態版本 |
| `updated_at` | `TIMESTAMPTZ` | Not null | 伺服器最後寫入時間 |

`state` 的最低結構：

```json
{
  "tripTitle": "2026 日本東京自由行 🎌",
  "members": [],
  "expenses": []
}
```

版本由伺服器管理，不信任瀏覽器時鐘。每次成功寫入時，資料庫以 `version = version + 1` 更新，回傳的新版本再放入記憶體狀態及 WebSocket 訊息。

## 資料流與同步規則

### 加入房間

1. 將房間 ID 正規化後查詢 RoomStore。
2. 資料庫已有房間時，載入並回傳伺服器狀態；客戶端快取不得覆寫。
3. 資料庫沒有房間時，以客戶端提供的有效快取建立房間；若客戶端也沒有有效快取，建立空房間與預設標題。
4. 將完整狀態與版本送給加入者。

### 修改資料

1. 驗證訊息種類與必要欄位。
2. 以伺服器記憶體中的目前狀態計算下一份完整狀態。
3. 呼叫 `save()`；只有資料庫成功後才更新記憶體並廣播。
4. 儲存失敗時不廣播成功事件，向操作端回傳 `SYNC_ERROR`，前端顯示同步失敗狀態並保留本機畫面資料供重試。

### 重新啟動

Render 程序重新建立後，記憶體中的 `rooms` Map 為空。第一位加入者會觸發資料庫讀取，恢復最新狀態；GitHub 內不再包含任何實際房間 JSON。

## 併發與一致性

現階段 Render 僅執行單一 Node.js 程序；同一房間的 WebSocket 訊息在後端依抵達順序更新。資料庫 `version` 為每次寫入遞增，客戶端只接受版本不舊於本機的伺服器事件。

`localStorage` 的毫秒時間戳不再具有伺服器資料的最終決定權，避免時鐘偏差或持有舊快取的瀏覽器覆蓋中央資料。若未來擴展為多個後端執行個體，需另行加入交易式比較版本及 PostgreSQL LISTEN/NOTIFY 或訊息服務；不在本次範圍內。

## 安全與設定

- `DATABASE_URL` 只從環境變數讀取，不寫入程式、測試檔或 Git。
- 正式環境的 PostgreSQL 連線使用供應商連線字串指定的 TLS 設定。
- SQL 使用參數化查詢；房間 ID 不拼接到 SQL。
- JSON 檔案名稱使用可逆且不碰撞的安全編碼，並忽略所有執行期房間 JSON。
- 健康檢查除了程序狀態，另回報儲存類型；不回傳連線字串或憑證。

## 既有未提交修改的處理

目前工作目錄已有房間快取命名空間、更新時間戳、WebSocket 回填及移除已提交房間 JSON 等修改。本次實作會保留有用的房間命名空間與即時事件格式，但會移除「較新的瀏覽器時間戳可覆寫既有伺服器資料」規則，改由 PostgreSQL 房間存在性與伺服器版本決定資料權威。其他非本需求修改不主動重構。

## 測試與驗收

使用 Node.js 內建測試執行器，測試儲存介面與 WebSocket 房間服務邏輯。最低驗收條件：

1. 首次加入不存在的房間可以建立資料。
2. 成員與支出修改會呼叫持久化儲存，成功後才廣播。
3. 以新的伺服器／房間服務實例連接同一個測試儲存後，能讀回先前資料。
4. 資料庫已有房間時，舊的客戶端快取不會覆蓋它。
5. 儲存失敗時不發送成功廣播，操作端收到同步錯誤。
6. 未設定 `DATABASE_URL` 時，本機 JSON 儲存仍能通過讀寫測試。
7. `npm test` 與 `npm run build` 均成功。

部署後以測試房間完成一次實際驗證：裝置 A 建立成員與支出，等待後端重新部署或重新啟動後，由裝置 B 使用相同房間網址讀回完全相同的資料。

## 部署步驟

1. 在 Neon 建立 PostgreSQL 專案與資料庫。
2. 將 Neon 提供的連線字串加入 Render Web Service 的 `DATABASE_URL` 環境變數。
3. 部署新版程式；啟動時自動建立 `rooms` 資料表。
4. 檢查 `/api/health` 顯示 PostgreSQL 儲存已就緒。
5. 以新的測試房間執行跨瀏覽器與重啟驗收。

現有線上 JSON 資料不保證仍是最新版本，因此不自動匯入 GitHub 中的房間檔案。部署前若仍有一台瀏覽器保有最新資料，第一次進入不存在的資料庫房間時可用該快取建立房間；建立後即以資料庫為唯一權威來源。
